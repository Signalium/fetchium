'fetchium': patch
---

Fixes for the microtask first fetch and refetches introduced with synchronous hydration and fast delivery.

- A query mounted and unmounted in the same task (a guard that redirects in a layout effect, a `replace` on mount, a route re-keyed in one commit) no longer leaves its relay rejected with an `AbortError` that the next mount shows. Its first request, which now starts before Signalium's deactivation flush, is left to finish in the background, as it did when the first fetch started on a timer, and the next mount shows its data. Releasing a `prefetch()` or `retain()` lease still aborts the fetch it started, in any task.
- A Signal param change made in the same task the query's last watcher leaves no longer sends a request that the deactivation then aborts. The refetch for a param change starts once Signalium's flush has run, which is in the same task when the change arrives through that flush.
- A query that reactivates stale in the same task the network goes offline waits for the network instead of rejecting with "Query is paused due to network status". The deferred refetch, a deferred restart and a debounced refetch recheck that the query is still active and not paused before they send.
- When a deactivation aborted the fetch in flight and the relay settled with the `AbortError`, the next activation refetches right away, as it already did for a relay still pending. A cached value is shown without the `AbortError` while it refetches. With no value yet, the relay is pending again but Signalium keeps reporting the previous error until the refetch lands. Callers awaiting the aborted fetch still get the `AbortError`. A query with a subscription (a topic query) that is unmounted before its first data, in a later task than it mounted, is not rejected at all: it stays pending, so its next mount reports no error while it refetches, and whoever awaits it gets that refetch's result, or an `AbortError` once the query is collected or the client destroyed.
- A Signal param set in the same task as the query mounts (an effect, a navigation that sets a param signal) no longer sends the old params and stores the result under the new params' key. The first fetch reads the params as they are when it starts.
- A param change while a fetch is in flight aborts that fetch and fetches the new params, instead of resolving the new params with the old params' response and persisting it under the new key (a bug in every earlier version). A response that arrives for params that are no longer current, from an adapter that ignores the abort, is dropped rather than applied or persisted. A param change also counts as invalidation, so a query reactivated after its params changed refetches even if its old data was fresh.
- A query whose result is not an entity keeps each params key's data under its own record. Its data lived in one record keyed by the params it was created with, so after a Signal param change every key's cached entry pointed at the newest params' data (a cold start for the old params showed the new params' data without a request), and another query showing the old params in memory was overwritten too (a bug in every earlier version). The query now shows a new result object for the new params; the previous params' data leaves memory unless another query still shows it, including when the query is collected. Caches written by earlier versions keep the shared record until each key is fetched again.
- A topic query (or any query with a running subscription) mounted and unmounted in the same task no longer stays pending forever on its next mount. Its first fetch may be waiting on the subscription the deactivation tears down, so it is aborted as before 0.6 rather than left to finish, and the next mount restarts it. `TopicQueryAdapter.send()` now honours the abort signal, so whoever awaits that first fetch gets the `AbortError` instead of waiting for the next mount (a bug in every earlier version). It rejects with an `AbortError` under React Native's `AbortController` polyfill too, whose signal carries no `reason`.
- The refetch for a Signal param change waits at most one task for Signalium's outstanding flush, instead of waiting until flushes stop being scheduled (a listener that keeps writing signals could hold it back indefinitely).
- With `reactivationStaggerMs`, refetches that a pause or an offline switch aborted are spread across the window again on resume, instead of all restarting at once.
- `QueryClient.destroy()` aborts every query's fetch in flight and cancels deferred ones, so nothing is written to the store after it (including a first fetch a same-task unmount left running, and a response that a replacement client sharing the store would otherwise be overwritten by). Whoever awaits a query it cancelled gets an `AbortError`, including a query whose first start or restart had not run yet.
- A restart that finds the network offline leaves the relay pending until the network returns, as before; if the query is unmounted first, the relay rejects with an `AbortError` and the next mount refetches, instead of leaving an awaiter waiting for that mount (a query with a subscription and no value stays pending instead, as above).
- A query whose first fetch a same-task unmount left running is collected (`gcTime`) once that fetch settles, not while it is still in flight: with `gcTime: 0` in a browser or React Native, collecting it earlier left the fetch's entities resident for good and its store write ignoring `destroy()`. A query the client collects has its work cancelled and its relay settled.
- A `__fetchNext()` page for params that changed while it was in flight is dropped, like a stale first page.
- With an asynchronous store, a Signal param change made while the cache load is pending no longer applies the old params' cached entry, and does not send the new params' request twice.
