Fixes for the entity snapshot fast path, unchanged-apply skipping and single-write events introduced in 0.6.0.

- Development builds hand out frozen snapshots, so a consumer that mutates one (a `sort()` in render, an assignment) fails at its own call site with a TypeError. Production snapshots stay mutable; treat them as read-only. The parser no longer writes into the objects it is given, so a snapshot (or part of one) handed back through a mutation event or a mutation's `effects` is read, not mutated, and two events sharing one nested object no longer make two entities share it. Event payloads are parsed into copies; a fetch result or a cached record is copied only where a parsed value differs from it, so an unchanged nested object, record or array costs no allocation, and a later merge into one the adapter froze goes into a copy.
- The dev-only stale-snapshot check no longer throws from inside a snapshot. A throw there escaped Signalium's watcher flush and stopped every consumer on the page from updating. It now serves the re-read value and raises the error out of band, once per field: through the client's `log.error` and then as an uncaught error (a red box in React Native, an uncaught error in the browser, a failed run under vitest). It compares with `Object.is` (so a `NaN` field no longer trips it, and `-0` over `0` is applied at every level), compares a rebuilt `Set` in linear time, and restores the key set of a snapshot a consumer altered.
- Hydrating a cached query no longer re-parses an entity that is already in memory. The re-parse ran already-parsed values through the parser again in place, wiping nested optional formats and parse results, and since the apply then saw no change it never notified; consumers of the first query kept stale snapshots. The in-memory data is used as-is once it structurally satisfies the query's shape, nested objects, arrays, records, unions and child entities included (members an array narrows out on read, and children that have left memory, are not held against it); otherwise the whole cached query is dropped and fetched, never served with an item missing. An entity built from streamed events is completed from its record instead.
- A streamed `create` (or an `update` for an entity not in memory) now writes the existing entities its payload changed, and the entities it created only once a written record references them: the root a live array retains is written before the event is routed (a write that fails is logged and nothing is routed, as a failed event always behaved), the rest follow from the records that reference them, and what nothing references is evicted at once, `gcTime` or not. A record's write puts its missing children first; a payload that links back to an ancestor defers both writes to the end of the apply. An entity built from events remembers the fields its events carried: its writes go through the store's new `mergeEntity`, which merges those fields over the record on disk, so the fields the events did not carry survive (a store without `mergeEntity` gets the whole in-memory data through `saveEntity`, as before 0.6). Once its fields are known to be the whole record (the store held no record of it when it was first written), it is written whole like any other entity, without reading the record back. An event that carries every field of the entity's class does not make it whole: another class sharing the typename, possibly not registered this session, may have written fields to the record that this class does not declare, and a merge keeps them. An event for an entity the store holds a record of (`hasEntity`) but that is not in memory refreshes that record the same way; a store that cannot say what it holds is not written, so no record nothing references is left behind. The store is asked only for a created root no live array retains, once per event: each such event costs one `hasEntity` call (a `kv.has` with `SyncQueryStore`).
- An entity that appears more than once in one payload (an author listed under `author` and again under `mentions`) is applied once: it keeps its child references and is written once.
- `_persisted` is only set once the store write succeeded, so a write that threw is retried by the next apply. `AsyncQueryStore` writers acknowledge processed entity writes (`onPersisted`), report a failed one, answer `hasEntity` from the keys they read from the delegate at start (alongside the queue, so writes do not wait for it; a queued write counts as held) and keep current, run `purgeStaleQueries` through the same serial queue as the writes (a reader with its own delegate still purges directly), ignore anything on the channel that is not one of their messages, and expose `isSettled()` and `hasQueuedDeletes()`; the client counts its own outstanding writes, so an acknowledgement of a write another instance queued does not mark a hydrated instance current. It does not skip a write while the writer has an operation queued that may delete the record the skip relies on (anything but the client's own entity writes); an entity whose own write is still queued counts as written, and an entity that one of the client's queued writes stops referencing is written again if it is referenced again before that write lands.
- `AsyncQueryStore` resizes a persisted LRU queue by copying it (growing no longer throws `RangeError`, shrinking evicts the dropped keys instead of stranding them, never the key being activated), and keeps a queue's persisted size for a message without `maxCount` from an older reader. `SyncQueryStore` gets the same resize.
- `onDelete` returns an unsubscribe and `QueryClient.destroy()` calls it, so a store no longer retains every client created against it. `SyncQueryStore` shares its delete listeners between every instance over the same backing kv.
- Reading a shared-typename entity array consumes the notifiers of the members it currently leaves out, so a reactive consumer learns when a member becomes eligible without a data change, and a consumer that only reads the array is not recomputed when a member it holds changes.
- Two classes sharing a typename: fields that are entity-free in one class but hold an entity through the other are no longer classified static for the snapshot fast path.
- A query whose cached value was rejected fetches even within `staleTime`; a query whose cached value was rejected fetches even within `staleTime`; snapshots of proxies created by a previous (hot-reloaded) module instance are walked instead of returned as-is.
